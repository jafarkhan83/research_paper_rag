# Research Paper RAG

Research Paper RAG is a FastAPI application that lets authenticated users ask questions about a research paper. It parses a PDF, separates the paper into sections, creates parent and child document chunks, embeds the child chunks in Chroma, retrieves relevant content with hybrid search, reranks the results with Cohere, expands the result with neighboring context, and generates an answer with Groq.

## What has been achieved

- User registration and login with password hashing and JWT authentication.
- Protected user routes using the authenticated user dependency.
- PDF text extraction with table detection and basic header/footer removal.
- Section extraction based on the configured research-paper headings.
- Parent-child chunking for more precise retrieval while preserving larger context.
- Hugging Face sentence embeddings for dense vector retrieval.
- Chroma as the vector database.
- BM25 as the sparse keyword retriever.
- Reciprocal Rank Fusion (RRF) to combine dense and sparse retrieval results.
- Cohere reranking of the fused results.
- Query rewriting with a Groq chat model before retrieval.
- Context expansion using neighboring child chunks and parent siblings.
- Final answer generation with a Groq chat model.
- Cached `ChatService` dependency so initialization is performed once per application process rather than for every request.

## RAG workflow

The application follows this flow:

1. A PDF is loaded by the parser.
2. Text and tables are extracted while header and footer regions are filtered.
3. Text is divided into sections using the configured headings.
4. Each section is stored as a parent, and its text is split into overlapping child chunks.
5. Child chunks receive metadata such as parent ID, position, page, section, and chunk ID.
6. Child chunks are embedded with `all-MiniLM-L6-v2` and stored in Chroma.
7. A user's question is rewritten into a concise search query.
8. Dense vector search and BM25 search each retrieve `k` chunks.
9. RRF combines the two result lists.
10. Cohere reranks the fused results and keeps the top `r` results.
11. Neighboring chunks are added according to `s`.
12. The original question and expanded context are sent to the answer-generation model.

## Retrieval parameters

The `/chat` endpoint requires three retrieval parameters.

### `k`

`k` defines the number of chunks retrieved by each retriever during the initial retrieval stage.

- Requirement: `k >= 2`
- Dense retrieval returns up to `k` chunks.
- Sparse BM25 retrieval returns up to `k` chunks.

### `r`

`r` defines how many results are retained by the Cohere reranker after dense and sparse results are fused.

- Requirement: `r >= 2`
- Requirement: `r <= k`
- `r` must not be greater than `k` because reranking cannot retain more results than were retrieved for the ranking input.

The validation condition in the retriever is:

```text
k >= 2
2 <= r <= k
```

### `s`

`s` controls how much neighboring context is added around the selected child chunk. It must be one of `1`, `2`, or `3`.

- `s = 1`: returns the selected child and its two neighboring sibling chunks.
- `s = 2`: returns the selected child and all sibling chunks belonging to the same parent.
- `s = 3`: returns the selected child, its siblings, and the children belonging to neighboring parent sections.

In short, `s` controls the amount of context supplied to the final answer model.

## Configuration

Create a `.env` file in the project root. Use your own values and never commit real credentials:

```env
COHERE_API_KEY=your-cohere-api-key
GROQ_API_KEY=your-groq-api-key
SECRET_KEY=your-long-random-jwt-secret
DATABASE_URL=mysql+pymysql://username:password@localhost:3306/research_paper_parser
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30
```

The database must exist before starting the application. The current database table creation call is commented out in `app/main.py`; create or migrate the database schema separately.

## Running the application

The current application uses imports such as `from routers...`, so start Uvicorn with the `app` directory as the working directory:

```powershell
cd D:\projects\project_3\app
uvicorn main:app --reload
```

The API is then available at:

```text
http://127.0.0.1:8000
```

Interactive API documentation is available at:

- Swagger UI: `http://127.0.0.1:8000/docs`
- ReDoc: `http://127.0.0.1:8000/redoc`

The default initializer expects the configured sample paper path and writes serialized chunks and the vector database to the configured project directories. Add the PDF used by `ChatService.initializer()` before calling the initialization endpoint.

```http

Content-Type: application/json
```

Request:

```json
{
  "email": "user@example.com",
  "password": "strong-password"
}
```

The response contains the JWT access token. Send that token on protected endpoints using:

```http
Authorization: Bearer <access-token>
```

### Health or greeting check

```http
GET /hello
```

Response:

```json
{
  "message": "Hello, World!"
}
```

### Initialize the research paper

```http
GET /initialize
Authorization: Bearer <access-token>
```

This parses the configured PDF, recreates the serialized parent and child chunk files, and creates the Chroma embeddings. It is intended as a one-time or deliberate re-indexing operation, not as part of every chat request.

Successful response:

```json
{
  "message": "Initialization complete!"
}
```

### Ask a question

```http
POST /chat
Authorization: Bearer <access-token>
Content-Type: application/json
```

Request:

```json
{
  "query": "What is the conclusion of this research paper?",
  "k": 4,
  "r": 2,
  "s": 3
}
```

Response:

```json
{
  "response": "Response: ..."
}
```

The `/chat` endpoint validates the retrieval parameters through the retrieval service. Invalid values return a client error response.

## Module details

### `parser.py`

Uses PyMuPDF to read PDF pages, detect tables, extract table content, remove likely header and footer text, and divide the paper into configured sections.

The current section headings are hardcoded:

```text
abstract
introduction
problem statement
objectives
methodology
results and discussion
conclusion
references
```

### `chunking.py`

Creates:

- Parent chunks representing complete section text.
- Child chunks of approximately 800 characters.
- 120-character overlap between child chunks.

Metadata connects each child to its parent and records its position, page, section, and unique chunk ID.

### `ingest.py`

Stores child documents and their Hugging Face embeddings in Chroma for later dense retrieval.

### `retriever.py`

Implements:

1. Dense retrieval with Chroma.
2. Sparse retrieval with BM25.
3. Reciprocal Rank Fusion.
4. Cohere cross-encoder-style reranking.
5. Validation for `k`, `r`, and the result count used for reranking.

### `utilities.py`

Provides serialization helpers, query rewriting, final response generation, and context-neighbor selection.

### `chat_service.py`

Coordinates initialization, query rewriting, retrieval, context expansion, and answer generation. The service is returned through a cached FastAPI dependency so the embedding model and chat models are not recreated for each request.

## Authentication and security notes

- Passwords are hashed before they are stored.
- Login creates a JWT containing the user identity.
- Protected endpoints require a valid bearer token.
- API keys, JWT secrets, and database credentials must be kept in `.env`.
- Do not commit `.env`, generated databases, serialized files, or production credentials.
- Replace development secrets before deploying.

## Remaining work

### User-specific paper ingestion and retrieval

Each user should be able to upload their own research paper and only embed and retrieve content from their own paper. Each paper needs a separate Chroma database or collection. A unique identifier, such as the user ID, must be attached to the paper name or storage key so the paper can be uniquely identified during ingestion and retrieval.

### Token tracking

Token usage tracking must be implemented so token consumption can be recorded for each user.

### Multiple papers per user

Each user should be able to upload more than one paper. The application should provide a list of that user's uploaded papers and allow the user to select which paper is used for ingestion and retrieval.

### User-configurable headings

The section headings are currently hardcoded. The application should provide two choices:

1. Let the user provide a custom array of heading names for better extraction and retrieval.
2. Use the current hardcoded heading list, with the understanding that it may not identify every heading in a paper.

### Additional production improvements

- Add a formal dependency file such as `requirements.txt` or `pyproject.toml`.
- Add automated tests for authentication, parsing, retrieval validation, and endpoint behavior.
- Add database migrations and enable controlled schema creation.
- Add upload validation, file size limits, and safe per-user storage.
- Add structured logging and production error handling.
- Move model and paper paths into configuration rather than fixed service constants.
